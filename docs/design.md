## 1. 概要

契約中のサブスクリプションや固定費、アーカイブなどの都度購入をまとめて管理し、「毎月いくら払っているか」を可視化するWebアプリ。請求日前のDiscord通知と見直し提案で無駄な支出を減らす。

将来的には家計簿アプリへ拡張することを前提とし、最初から「支出の記録」をデータの中心に置いた設計にする。

| 項目 | 内容 |
|---|---|
| 形態 | Webアプリ（PC・スマホ両対応のレスポンシブ） |
| 利用者 | 当面は自分のみ。将来的に家族共有を想定 |
| 主な目的 | 固定費・都度購入の可視化、請求日の把握、解約し忘れ防止 |
| 将来の拡張 | 家計簿（収入・変動費の記録、予算管理）、家族共有 |

## 2. 全体構成（モジュール）

1つのアプリの中に機能をモジュールとして追加していく構成にする。

| モジュール | 時期 | 内容 |
|---|---|---|
| 固定費・サブスク | 第1段階 | 定期的に支払うものの管理、通知、見直し提案 |
| 都度購入 | 第1段階 | アーカイブ・単発コンテンツなど不定期に買うものの記録と集計 |
| 家計簿 | 第2段階 | 収入、食費などの変動費、月ごとの予算と収支 |
| 共有 | 第3段階 | 家族とのデータ共有、権限管理 |

3つのモジュールはすべて「支出記録（transactions）」テーブルを共有する。サブスクの請求日が来ると支出記録が自動で1件作られ、都度購入は手動で支出記録を追加する。こうしておくと、家計簿モジュールを追加したときに既存データをそのまま「固定費」「娯楽費」として集計できる。

## 3. 機能要件

### 3.1 サブスク・固定費の登録
- サービス名、購入先、金額、支払いサイクル（月額／年額／週額／その他）、次回請求日、カテゴリ、支払い方法、メモを登録・編集・削除できる
- 状態を管理できる（詳細は 3.9）
- 金額の変更（値上げ等）に対応する（詳細は 3.10）
- 無料トライアルの終了日を登録できる
- 外貨建て（米ドル等で請求されるもの）にも対応する（詳細は 3.7）
- 光熱費など、毎月金額が変わる固定費にも対応する（詳細は 3.14）
- 引き落とし口座は、支払い方法を通じて記録する（支払い方法ごとに引き落とし口座を選ぶ。5. bank_accounts）。口座ごとの月の引き落とし合計を確認できるようにする

### 3.2 都度購入（アーカイブ等）の記録
- 購入日、品名（例：◯月◯日配信のアーカイブ）、金額、購入先（配信者・サービス・シリーズ名など。一覧から選択、詳細は 3.12）、カテゴリ、メモを記録できる
- 購入先ごと・月ごとの合計を表示する
- 都度購入用の月予算を設定でき（初期状態は未設定。1〜2か月の実績を見て決める）、超過しそうなとき（初期値：80%）と超過したときにDiscordへ通知する
- よく使う購入先・金額をテンプレートとして保存し、ワンタップで記録できるようにする

### 3.3 月額・年額の合計表示
- 利用中のサブスクについて、月額換算・年額換算の合計を表示する
  - 年額 → 月額換算：金額 ÷ 12
  - 週額 → 月額換算：金額 × 52 ÷ 12
- 今月の支出合計を「固定費」と「都度購入」に分けて表示する
- 数え方のルール
  - **今月の支出**：その月に実際に請求・購入された金額（年額サブスクは請求月に全額を計上）。家計簿の実際のお金の動きと一致させる
  - **サブスク月額合計**：年額・週額を月額に按分した金額。「毎月平均いくらかかっているか」を示す
  - 画面上ではこの2つの違いが分かるよう、ラベルや補足説明を付ける
- 「解約検討中をすべて解約した場合の節約額」を表示する

### 3.4 Discord通知
- DiscordのWebhook（チャンネルにメッセージを送るためのURL）を使い、指定したチャンネルへ通知する
- 通知の種類

| 通知 | タイミング | 内容の例 |
|---|---|---|
| 請求日前 | 次回請求日のN日前（初期値3日前、項目ごとに変更可） | 「3日後にNetflix 1,490円の請求があります」（自分で購入するもの（3.14）は「3日後は◯◯の購入予定日です（目安：2,000円）」） |
| トライアル終了前 | 終了日の前日 | 「明日で◯◯の無料期間が終わります」 |
| 予算アラート | 都度購入が月予算の80%・100%に達したとき | 「今月のアーカイブ購入が予算の80%に達しました」 |
| 月次レポート | 毎月1日の朝8時 | 先月の支出合計、今月の請求予定、見直し候補の件数 |
| 入力リマインド | 都度購入の記録が7日間ない場合に週1回 | 「最近アーカイブなどの購入はありませんでしたか？記録はこちら → (URL)」 |
| 確定額の入力 | 外貨建て・金額が変動する固定費の請求から数日後 | 「◯◯の今月の請求額（円）が確定したら入力してください（目安：1,580円）」 |
| バックアップのリマインド | 最後のエクスポートから7日以上経過したとき（週1回まで） | 「前回のバックアップから◯日経っています。アプリの設定画面からバックアップファイルを保存してください → (URL)」 |
| 定期実行の異常 | 定期処理が失敗したとき | 「定期処理でエラーが発生しました」 |

- 1日1回、毎朝8時に定期実行し、該当するものをまとめて1メッセージで送る（Discord の文字数上限を超える場合は分けて送る）
  - Vercel の無料プラン（Hobby）の定期実行は、指定した時刻の1時間の中のどこかで実行される（2026年10月時点の情報。本番準備時に確認する）。そのため実際の通知は8時台になる
  - 実行時刻は定期実行の設定ファイル（vercel.json）で固定するため、アプリの画面からは変更できない。変更したい場合は設定ファイルを書き換えて反映する
  - vercel.json（JSON）にはコメントを書けないため、時刻（UTC 23:00 ＝ 日本時間 8:00）の説明は定期実行 API のコード（src/app/api/cron/daily/route.ts）に残す
- 請求日を過ぎたサブスクは次回請求日を自動更新し、支出記録を1件作成する

### 3.5 カテゴリ別のグラフ
- カテゴリ別の月額割合を円グラフ（ドーナツ）で表示
- 月ごとの支出を棒グラフで表示し、固定費と都度購入を積み上げで色分けする
- カテゴリ初期値：動画、音楽、ゲーム、配信・アーカイブ、クラウド・ソフト、通信、住居・光熱、保険、その他

### 3.6 解約検討リスト・見直し提案
- サブスクごとに「利用頻度」（よく使う／ときどき／ほぼ使わない）と「最終利用日」を記録できる
- 以下のルールで見直し候補を自動抽出する

| ルール | 条件の例 | 表示メッセージの例 |
|---|---|---|
| 低頻度・高額 | 利用頻度が「ほぼ使わない」かつ月額換算が基準額以上 | 「あまり使っていないのに月◯円かかっています」 |
| 長期未使用 | 最終利用日から30日以上経過 | 「最後に使ってから◯日経っています」 |
| 同カテゴリ重複 | 同じカテゴリに利用中が2件以上 | 「動画サービスが3件あります」 |
| 年額プラン検討 | 月額払いで1年以上継続中 | 「年額プランにすると安くなるかもしれません」 |
| トライアル終了間近 | 終了日まで3日以内 | 「無料期間がまもなく終わります」 |
| 都度購入の定額化 | 同じ購入先への都度購入の月平均が基準額以上 | 「◯◯のアーカイブに月平均◯円使っています。メンバーシップ等の定額プランがあれば検討してみては？」 |

- 提案から「解約検討中にする」「今回は無視する」を選べる

### 3.7 外貨建てサブスクへの対応
- サブスクに通貨（USD、EURなど）と外貨金額を登録できる
- 支払い方法ごとに「海外事務手数料率」（例：クレジットカードで1.6〜2.5%程度。カードによって異なる）を設定できる
- 円換算の目安額 ＝ 外貨金額 × 為替レート × (1 ＋ 海外事務手数料率)
- 為替レートは定期実行で1日1回、無料の為替APIから取得して保存する（候補：Frankfurter など。採用時に利用条件を確認）
- 合計表示やグラフでは目安額を使い、画面上に「目安」と分かる表示をする
- 請求時に作られる支出記録は「目安」状態で作成し、カード明細で確定した円の金額を後から入力すると「確定」に変わる
- 確定額と目安額の差から、実際にかかった手数料率を確認できる（任意）

### 3.8 システムの維持（Supabaseの停止対策）
Supabaseの無料プランは、一定期間アクセスがないとプロジェクトが一時停止される仕様がある（2026年6月時点の情報。実装時に条件を確認する）。入力をさぼっても止まらないよう、以下の仕組みを入れる。

- **毎日の定期実行で必ずデータベースに書き込む**：通知のための定期処理（Vercel Cron）が毎日動き、その実行結果を「定期実行ログ」テーブルに1行記録する。為替レートの保存も毎日行うため、ダミーデータを追加・削除しなくても、意味のあるデータで自然に毎日アクセスが発生する
- **予備の定期実行**：Vercel Cronが止まった場合に備え、GitHub Actionsの定期実行から週1〜2回、同じ死活確認用のAPIを呼び出す
- **異常の検知**：定期実行ログの最終実行日時が2日以上前になっていたら、予備の定期実行からDiscordに警告を送る
- **バックアップ**：バックアップファイルは外部サービスに自動送信せず、アプリの設定画面から自分でエクスポート（JSON / CSV）して保存する。最後にエクスポートした日時を記録し、7日以上経過したらDiscordにリマインドのメッセージだけを送る（ファイルは添付しない）
- 万一停止した場合は、Supabaseの管理画面から再開できる（再開できる期限などの条件は実装時に確認）

### 3.9 状態の管理（解約・一時停止）
| 状態 | 値 | 意味 | 合計への算入 |
|---|---|---|---|
| 利用中 | active | 通常どおり契約中 | 算入する |
| 解約検討中 | considering | 解約を検討している | 算入する（節約見込み額の計算対象） |
| 解約手続き済み | cancel_scheduled | 解約したが、利用終了日までは使える | 次回請求は発生しないものとして扱う |
| 一時停止中 | paused | サービス側で一時停止している | 算入しない。再開予定日があれば登録できる |
| 解約済み | cancelled | 利用終了日を過ぎた | 算入しない |

- 「解約手続き済み」にするときは利用終了日を登録する。終了日の前日にDiscordで通知し、終了日を過ぎたら自動で「解約済み」に変わる
- 解約手続き済みのサービスに請求が発生していないかを確認できるよう、終了日以降に支出記録が作られた場合は警告を出す
- 一時停止中は、再開予定日の数日前に通知する

### 3.10 金額の変更（値上げ等）
- 金額を変更しても、過去の支出記録の金額は変えない
- 変更には「いつの請求分から新しい金額にするか（適用日）」を指定でき、適用日より前の請求は旧金額、以降は新金額で記録する
- 「◯月から値上げ」のような将来の変更予定を事前に登録できる。適用日の前の請求日前通知で、値上げ後の金額であることを知らせる

### 3.11 請求日のルール
- 月額：「毎月◯日」で登録する。その月に該当日がない場合（例：31日請求の2月）は、その月の末日を請求日とする
- 年額：「毎年◯月◯日」で登録する。2月29日の場合は、うるう年以外は2月28日とする
- 週額：「毎週◯曜日」で登録する
- その他（3か月ごとなど）：「◯か月ごと」と基準日で登録する
- 次回請求日は上記のルールから自動計算し、必要に応じて手動で上書きできる

### 3.12 購入先の管理
- 購入先（配信者・サービス・店舗など）を一覧として登録し、サブスクと都度購入の両方から選んで紐付ける（表記ゆれによる集計の分裂を防ぐ）
- 入力中に一覧にない名前を入力した場合は、その場で新しい購入先として追加できる
- 購入先ごとに、サブスクと都度購入を合わせた月の支出合計を確認できる（例：ある配信者のメンバーシップ＋アーカイブ購入の合計）
- 似た名前の購入先を1つにまとめる（統合する）機能を用意する

### 3.13 入力負担の軽減
入力をさぼっても破綻しにくく、最小限の操作で記録できることを重視する。

- サブスク登録の必須項目は、サービス名・金額・支払いサイクル・次回請求日のみとする。カテゴリ、支払い方法、利用頻度、メモなどは後から入力できる（未入力の項目がある場合は一覧でさりげなく表示する）
- 通貨の初期値は円とし、外貨の場合だけ切り替える
- 都度購入は、テンプレートまたは「前回と同じ内容で記録」からワンタップで記録でき、金額と日付だけ直せばよい形にする
- 購入日の初期値は今日にする
- 入力を忘れていた期間があっても、後からまとめて記録できるようにする（日付を過去にして登録できる）

### 3.14 金額が変動する固定費（光熱費など）
電気代・ガス代・水道代など、請求日は決まっているが金額が毎月変わるものは、外貨建て（3.7）と同じ「目安額 → 確定額」の流れで扱う。

- サブスクの登録時に「金額が毎月変わる」を選べる。このとき登録する金額は目安額（だいたいの月額）とする
- 請求日に作られる支出記録は「目安」状態で作成し、検針票や明細で確定した金額を後から入力すると「確定」に変わる
- 確定額の入力リマインドは、外貨建てと同じ通知で送る（3.4）
- 月額合計やグラフでは、確定額があればそれを使い、なければ目安額を使う。目安額は画面上で「目安」と分かるように表示する
- 目安額は手入力とする（直近の確定額から自動で計算する方法は、使い始めてから検討する）

**自分で購入する毎月のもの**
自動引き落としではなく、自分で買いに行く毎月のもの（定期的に買う商品など）も、「金額が毎月変わる」＋毎月払いとして同じ流れで扱う。

- サブスクの登録時に「自分で購入する（is_manual_purchase）」を選べる。このとき「金額が毎月変わる」も有効にする
- 買う日は決まっていないため、請求日は「毎月◯日ごろ」の目安日として扱う（請求日のルールは 3.11 の月額と同じ）
- 確定額を入力するときに、実際の購入日も修正できる。重複防止は元の請求予定日（transactions.billing_date）で行うため、購入日を変えても影響しない
- 請求日前通知は「請求があります」ではなく「購入予定日です」のような表現にする（3.4）

| S2 | 一覧 | 「サブスク」「都度購入」のタブ切り替え。絞り込み・並び替え |

| S4 | 見直し | 見直し提案、解約検討リスト、節約見込み額 |
| S5 | 設定 | Discord Webhook、通知のタイミング（請求日の何日前か等）、都度購入の月予算、カテゴリ、バックアップ（エクスポートと前回の保存日時） |

### ナビゲーション
- PC：左サイドバーに S1・S2・S4・S5
- スマホ：下部タブバーに同じ4つ。中央または右下の「＋」ボタンから S3 を開く
- 将来の家計簿モジュールは、ナビゲーションに「家計簿」タブを追加する形で組み込む

### 画面ごとの要素（ラフ）

**S1 ダッシュボード**
- 上部カード：今月の支出合計（内訳：固定費／都度購入）、サブスク月額合計、年額合計
- 都度購入の予算バー（今月の使用額／予算）
- 今後30日の請求予定リスト
- カテゴリ別ドーナツグラフ、月別支出の積み上げ棒グラフ
- 「見直し候補が◯件あります」バナー → S4

**S2 一覧**
- サブスクタブ：サービス名、カテゴリ、金額（サイクル）、次回請求日、状態バッジ
- 都度購入タブ：月ごとに見出しを付け、購入日・品名・購入先・金額を表示。購入先での絞り込み

**S3 登録・編集**
- サブスク：金額とサイクルを入れると月額換算をその場で表示

**S4 見直し**
- 上部：解約検討中をすべて解約した場合の節約額（月・年）
- 提案カード（ルール名、理由、対象、アクションボタン）
- 解約検討中リスト

## 5. データ設計

### 5.0 共通ルール
- ID は UUID とする
- 金額の型
  - 円の金額は整数（integer）で保存する（小数による計算誤差を防ぐ）
  - 外貨の金額、為替レート、手数料率は十進数型（numeric）で保存する。浮動小数点型（float）は使わない
  - 外貨から円に換算した金額は、1円未満を四捨五入して整数にする
- 日付・日時の型は 9.2 に従う（日付は date、日時は timestamptz）
- 以下の表の「number」は、上記ルールに従って integer または numeric を使い分ける

家族共有に備えて、原則としてすべてのデータに「どの世帯のものか（household_id）」を持たせる。当面は自分だけの世帯が1つあるだけだが、後から共有機能を追加してもデータ構造を作り直さずに済む。

household_id を持たないテーブルは、以下のルールでアクセスを制御する（7.1）。

| テーブル | 世帯の判定・アクセスのルール |
|---|---|
| users | ログイン中のユーザー本人の行だけ読み書きできる |
| households | 自分がメンバーになっている世帯だけ読める |
| subscription_price_changes | 対象のサブスク（subscriptions）の household_id で判定する |
| exchange_rates | 全世帯共通のデータ。ログイン中のユーザーは読むだけ。書き込みはサーバー側の定期実行（service_role）からのみ |
| job_runs | システムの記録。書き込みはサーバー側の定期実行（service_role）からのみ。画面で使う場合（9.4の警告表示など）も読むだけとする |
| allowed_emails | ログインを許可するメールアドレス。画面からは読み書きできない。ユーザー作成前のフック（認証サービスの権限）だけが読む。本番ではSQLで直接登録する |

## 6. 非機能要件
- 金額などの個人情報を扱うため、HTTPSで公開し、ログインしないとアクセスできないようにする
- ログインはGoogleアカウントで行う（Supabaseの認証機能を利用）。当面は自分のアカウントだけが使えるよう制限する
- 世帯ごとにデータを分離し、他の世帯のデータが見えないようにする（共有機能を見据えて最初から実装）
- Discord Webhook URLは他人に知られるとチャンネルに投稿されてしまうため、コードやGitHubに直接書かない
- データのエクスポート（CSV / JSON）でバックアップできるようにする
- スマホで片手操作しやすいレイアウトにする
- デザインは落ち着いた配色とし、ライトモード・ダークモードの両方に対応する（端末の設定に合わせて切り替え）
- 基本的に無料枠の範囲で運用する

## 7. セキュリティ

支出データという個人情報をインターネット上で扱うため、以下の対策を行う。7.1〜7.3 は最優先で、最初の実装時から必ず入れる。

### 7.1 アクセス制御（最優先）
- Supabaseの全テーブルで行単位のアクセス制御（RLS：Row Level Security）を有効にする
  - ブラウザに埋め込まれる公開用の鍵（anon key）は誰でも見られる前提で考え、RLSで守る
  - ルールは「ログイン中のユーザーが household_members に登録されている世帯のデータだけ読み書きできる」とする
  - household_id を持たないテーブル（為替レート、定期実行ログなど）は、5.0 の表のルールに従う
  - 新しいテーブルを作るときは、RLSの有効化とルール作成を必ずセットで行う
- Googleログインで誰でも新規登録できないようにする
  - 当面は許可したメールアドレス（自分のみ）以外のログインを拒否する。判定はユーザー作成前のフックで行い、許可メールは allowed_emails テーブルで管理する（5.）
  - 家族共有の段階で、招待されたユーザーだけが登録できる仕組みに変更する
- 未ログイン状態では、ログイン画面以外のページとAPIにアクセスできないようにする

### 7.2 秘密情報の管理（最優先）
| 秘密情報 | 用途 | 保存場所 | 注意点 |
|---|---|---|---|
| Supabase service_role key | 定期実行など、サーバー側で全データを扱う処理 | Vercelの環境変数 | RLSを無視できるため、ブラウザに絶対に渡さない。環境変数名に `NEXT_PUBLIC_` を付けない |
| Discord Webhook URL | 通知の送信 | Vercelの環境変数 / GitHub Secrets | 漏れるとチャンネルに投稿され放題になる。漏れた場合はDiscord側でWebhookを削除して作り直す |
| CRON_SECRET | 定期実行APIの認証 | Vercelの環境変数 / GitHub Secrets | 推測されにくい長いランダム文字列にする |
| Google OAuth のクライアントシークレット | Googleログイン | Supabaseの管理画面 | アプリのコードには書かない |

- `.env` 系のファイルは `.gitignore` に入れ、Gitに含めない
- GitHubリポジトリは公開にする。無料プランでは非公開リポジトリにブランチ保護を使えず、main を PR と CI の成功なしに変更できないようにするため。公開にあたって次を守る
  - 秘密情報（上の表のもの）、実際の契約内容、個人のメールアドレスをコミットしない。テストデータは `example.com` のアドレスと架空の契約で作る
  - コミットは GitHub の noreply アドレス（`ID+ユーザー名@users.noreply.github.com`）で行う。GitHub のメール設定で「Keep my email addresses private」と「Block command line pushes that expose my email」を有効にする
  - GitHub のシークレットスキャンとプッシュ保護（鍵を含む push を拒否する機能）を有効にする
  - main はブランチ保護で、PR と CI の成功を必須にする
- Webhook URLなどをログやエラーメッセージに出力しない

### 7.3 定期実行APIの保護（最優先）
- 通知・為替取得・死活確認などの定期実行用APIは、リクエストに正しい `CRON_SECRET` が付いているときだけ処理する
- 1日に同じ処理が何度も呼ばれても、通知が重複しないようにする（その日の実行済みを定期実行ログで確認する）
- 請求日の支出記録の自動作成も重複しないよう、データベースの一意制約（subscription_id と billing_date の組み合わせ）で防ぐ
- 外部の為替APIから受け取った値は、数値の範囲などを確認してから保存する

### 7.4 外部サービスに送る情報
- Discordに送るのは通知メッセージのみとし、データのファイル添付は行わない
- 通知に含めるのはサービス名・金額・日付程度にとどめ、支払い方法の詳細、引き落とし口座、メモは含めない
- 通知先は自分だけが参加するサーバーの非公開チャンネルにする

### 7.5 入力値と出力の扱い
- 入力値はブラウザ側だけでなくサーバー側（またはデータベースの制約）でも形式をチェックする（金額は数値、日付は正しい日付など）
- URL欄は `http://` または `https://` で始まるものだけを受け付ける（`javascript:` などの危険なリンクを防ぐ）
- 画面表示はReactの標準の仕組みで行い、HTMLをそのまま埋め込む書き方（dangerouslySetInnerHTML）は使わない
- CSVエクスポートでは、`=`、`+`、`-`、`@` などで始まる値の先頭に `'` を付け、Excelで開いたときに数式として実行されないようにする（CSVインジェクション対策）

### 7.6 アカウントと依存パッケージ
- Google、GitHub、Vercel、Supabase、Discordのすべてのアカウントで2段階認証を有効にする（どれか1つが乗っ取られると全データに届く可能性があるため）
- GitHubのDependabotを有効にし、パッケージの脆弱性や更新を通知してもらう
- パッケージのバージョンは固定し（lockファイルをコミットする）、更新は内容を確認してから行う

### 7.7 バックアップとデータ消失への備え
- バックアップは設定画面からのエクスポートで行い、保存したファイルは自分のPCやクラウドストレージの非公開の場所に置く
- 最後のエクスポートから7日以上経過したらDiscordでリマインドする（3.4）
- 誤操作に備え、削除は確認ダイアログを出す。重要なデータ（支出記録など）は一定期間ゴミ箱に残す方式も検討する

### 7.8 家族共有に向けて
- RLSのルールを最初から「世帯のメンバーかどうか」で判定しておき、共有時はメンバー追加だけで済むようにする
- 招待の方法（招待リンクの有効期限など）と、メンバーごとの権限（閲覧のみ／編集可）は共有機能の実装時に決める
- 許可メールの確認（allowed_emails）はアカウントの新規作成時にだけ行われる。一度登録されたアカウントは allowed_emails から外してもログインできるため、メンバーを外すときは認証のアカウント（auth.users）の削除や世帯メンバーからの除外もあわせて行う仕組みにする

### 7.9 実装時のチェックリスト
- [ ] 全テーブルでRLSが有効になっている（Supabaseの管理画面のセキュリティ診断機能でも確認する）
- [ ] 許可したメールアドレス以外でログインできない
- [ ] ブラウザの開発者ツールで見える範囲に service_role key や Webhook URL が含まれていない
- [ ] `.env` がGitに含まれていない
- [ ] 定期実行APIを `CRON_SECRET` なしで呼ぶと拒否される
- [ ] 関連サービスすべてで2段階認証が有効になっている
- [ ] Dependabotが有効になっている
- [ ] リポジトリに秘密情報・実際の契約内容・個人のメールアドレスが含まれていない
- [ ] コミットの作者が noreply アドレスになっている

## 8. 技術構成

### 採用構成
言語はフロントエンド・バックエンドともに TypeScript で統一する（データベースの定義・アクセス制御・集計は SQL）。

| 区分 | 役割 | 技術 | 言語・形式 |
|---|---|---|---|
| フロントエンド | 画面の作成 | Next.js（React） | TypeScript（画面は TSX） |
| フロントエンド | 見た目・レイアウト | Tailwind CSS（v0.11で確定） | CSS（クラス名で指定） |
| フロントエンド | グラフ | Recharts | TypeScript |
| フロントエンド | 入力チェック | Zod（サーバー側と共通で使う） | TypeScript |
| バックエンド | サーバー処理・API | Next.js のサーバー機能（Route Handlers / Server Actions）、Vercel 上で実行 | TypeScript |
| バックエンド | データベース | Supabase（PostgreSQL、無料プラン） | SQL（テーブル定義、RLS、集計ビュー） |
| バックエンド | ログイン | Supabase Auth（Googleログイン） | 設定中心。呼び出しは TypeScript |
| バックエンド | 定期実行（通知・為替取得・ログ記録） | Vercel Cron Jobs（毎日） | 設定は JSON、処理は TypeScript |
| バックエンド | 予備の定期実行（死活確認） | GitHub Actions（週1〜2回） | YAML |
| 外部連携 | 通知 | Discord Webhook | TypeScript から HTTP で送信 |
| 外部連携 | 為替レート | 無料の為替API（Frankfurter など） | TypeScript から HTTP で取得 |
| 開発 | テスト | Vitest（ロジック）、RLS のテスト | TypeScript / SQL |
| 開発 | 自動チェック | GitHub Actions（CI） | YAML |

選定理由：
- 支出記録・世帯・カテゴリなど表同士の関係が多く、家計簿への拡張では集計も増えるため、表形式のデータベース（PostgreSQL）が向いている
- Supabaseはログイン機能と「行ごとのアクセス制限」（自分の世帯のデータしか読めない設定）を持っており、家族共有を後から追加しやすい
- 通知は1日1回で十分なので、無料の定期実行で賄える
- 画面とサーバー処理を1つのプロジェクトで TypeScript だけで書けるため、データの型を両方で共有でき、学習する言語も少なくて済む

### 比較した他の構成（不採用）
| 構成 | 長所 | 注意点 |
|---|---|---|
| Next.js + Firebase | ログインやスマホ通知との相性が良い | データベースが表形式ではないため家計簿の集計がやや面倒。サーバー側の定期実行には従量課金プランへの登録が必要 |
| Cloudflare Workers + D1 | 無料枠が広く、定期実行も無料で使える | 情報や事例がやや少なく、慣れるまで時間がかかる |
| Python（FastAPI）+ SQLite + 自前サーバー | 構成が単純でPythonの経験を活かせる | 常時動かす無料サーバーの確保が難しい |

※無料プランの条件（容量、休止の条件、定期実行の回数や実行時刻の正確さなど）は変わることがあるため、実装開始時に各サービスの公式ページで確認する。特にSupabaseの無料プランは、しばらくアクセスがないとプロジェクトが一時停止される仕様があったため、毎日の定期実行で利用が続くか確認しておく。

## 9. 実装方針

### 9.1 段階的な開発範囲
一度にすべてを作らず、使える状態を早めに作ってから機能を足していく。各段階の終わりで実際に使い始め、使い勝手を見て次の段階の内容を調整する。

| 段階 | 名称 | 内容 | 完了の目安 |
|---|---|---|---|
| 1 | MVP（最小限で使える版） | Googleログイン（許可メールのみ）、世帯の自動作成、サブスクの登録・編集・一覧、請求日のルール（3.11）、月額・年額合計の表示、請求日前のDiscord通知、定期実行ログ（停止対策を含む）、セキュリティの最優先項目（7.1〜7.3） | 実際のサブスクを登録し、Discordに通知が届く |
| 2 | 支出記録と外貨 | 請求日の支出記録の自動作成、状態の管理（3.9）、金額の変更（3.10）、支払い方法と引き落とし口座、外貨建て対応と為替取得（3.7）、金額が変動する固定費（3.14）、確定額の入力 | 外貨建てサブスクと光熱費の目安額と確定額が記録できる |
| 3 | 都度購入 | 購入先の管理（3.12）、都度購入の記録・テンプレート、月予算と予算アラート、入力リマインド | アーカイブ購入をワンタップで記録できる |
| 4 | 可視化と見直し | ダッシュボードの完成、カテゴリ別・月別グラフ、見直し提案（3.6）、月次レポート | 月次レポートが届き、見直し候補が表示される |
| 5 | 仕上げ | バックアップ（エクスポートとリマインド）、予備の定期実行（GitHub Actions）、7.4〜7.7の対策、チェックリスト（7.9）の確認 | チェックリストをすべて満たす |
| 6 | 家計簿 | 家計簿モジュールを追加（内容は別途検討） | ― |

※ データ設計（household_id、transactions など）は段階1から最終形に沿って作り、後の段階で作り直しが発生しないようにする。使わないテーブルは、必要になった段階で追加してよい。

※ 段階1では支出記録を作らないため、請求日を過ぎたサブスクは次回請求日だけを自動で進める。支出記録の自動作成は段階2から始め、段階1の期間に過ぎた請求日の分はさかのぼって作らない。

### 9.2 日付と時刻の基準
- アプリ内の日付の判定・計算（請求日、通知日、月の区切りなど）はすべて日本時間（Asia/Tokyo）で行う
- 日付だけを扱う項目（請求日、購入日など）は、時刻を持たない日付型（date）で保存する
- 日時を扱う項目（作成日時、定期実行の開始時刻など）は、タイムゾーン付き（timestamptz）で保存し、表示時に日本時間へ変換する
- Vercel Cron は世界標準時（UTC）で指定するため、「毎朝8時（日本時間）」は UTC の前日23時として設定する。設定ファイルにはその旨をコメントで残す
- 「今日」を求める処理は共通の関数にまとめ、必ず日本時間で計算する
- 月末・うるう年・年またぎの日付計算はテストを書いて確認する

### 9.3 開発環境と本番環境
| 環境 | データベース | 用途 | 通知 |
|---|---|---|---|
| 開発 | 自分のPC上で動かすSupabase（Supabase CLI） | 機能の開発・動作確認 | テスト用のDiscordチャンネル（本番とは別のWebhook） |
| 本番 | クラウドのSupabase（無料プラン） | 実際の利用 | 本番用のDiscordチャンネル |

- テーブルの作成・変更（RLSのルールを含む）はマイグレーションファイルとして記録し、Gitで管理する。本番への反映はこのファイルを使って行い、管理画面から直接変更しない
- 開発用のテストデータ（サンプルのサブスクなど）は投入用のファイルを用意し、いつでも作り直せるようにする
- 実際の契約内容を使わずに開発を進めるため、テストデータには扱いにくいケースをわざと含める
  - 毎月31日請求（2月・4月など末日が31日でない月の扱い）
  - 2月29日の年額
  - 週額、3か月ごとの請求
  - USD建て（為替レートと海外事務手数料率の計算）
  - 金額が変動する固定費（光熱費）
  - 無料トライアル中のもの
  - 解約手続き済みで利用終了日が近いもの、一時停止中のもの
  - 将来の値上げ予定が登録されているもの
- テストデータは実在のサービス名を使ってもよいが、金額や請求日は自分の実際の契約内容にしない
- 本番のデータを開発環境にコピーしない
- 環境変数は環境ごとに分け、開発環境で本番の鍵やWebhook URLを使わない
- コードの公開は、GitHubのメインブランチに反映したときにVercelが自動で本番に公開する形とする

### 9.4 通知の送信に失敗したときの扱い
- Discordへの送信に失敗した場合は、間隔を空けて最大3回まで再送する
- それでも失敗した場合は、定期実行ログ（job_runs）に失敗と未送信の内容を記録する
- 翌日の定期実行で未送信の通知を確認し、その日の通知と一緒に「前日に送れなかった通知」として送る
  - 未送信の通知は、サブスクIDと請求日を定期実行ログ（job_runs.detail に JSON 文字列）に記録する。再送時は、そのサブスクが削除・解約されておらず請求日も変わっていない場合だけ、その日の日付で文面を作り直して送る
- 請求日をすでに過ぎた通知など、時期を逃して意味がなくなったものは再送せず、「◯件の通知を送れませんでした」とだけ伝える
- 2日以上連続で送信に失敗している場合は、アプリのダッシュボードに警告を表示する（Discord自体に届かない可能性があるため）

### 9.5 型の自動生成
- Supabase のテーブル定義から TypeScript の型を自動生成し（Supabase CLI の型生成機能）、データベースを扱うコードはすべてこの型を使う
- マイグレーションでテーブルを変更したら、型を生成し直してコミットする
- 入力チェック（Zod）の定義は画面とサーバーで共通にする

### 9.6 テスト
- 日付計算（請求日の算出、月末・うるう年・年またぎ、日本時間と UTC のずれ）は Vitest で網羅的にテストする
- 金額計算（月額換算、外貨換算と丸め、節約見込み額）もテストする
- RLS について「他の世帯のデータを読み書きできないこと」「未ログインで何も読めないこと」を確認するテストを用意する
- 見直し提案のルールは、条件に当てはまる／当てはまらないデータでテストする

### 9.7 データベースでの集計
- 月別・カテゴリ別・購入先別の合計など、繰り返し使う集計は SQL のビューとして用意し、画面側ではビューを読むだけにする
- ビューにも RLS が効くように、作成時に `security_invoker = true` を指定する（PostgreSQL のビューは、指定しないと作成者の権限で実行され、RLS が効かないため）
- 家計簿モジュールでも同じビューを再利用・拡張できる形にする

### 9.8 自動チェック（CI）
- GitHub に変更を反映するたびに、GitHub Actions で以下を自動実行する
  - 型チェック
  - コードの書式・ルールのチェック（ESLint、Prettier など）
  - テスト（9.6）
- チェックに失敗した変更は本番に反映しない（メインブランチへの反映前にチェックを通す）
- Dependabot の更新もこのチェックを通ってから取り込む
